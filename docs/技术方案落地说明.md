### 1.1 分层与依赖方向

```
        ┌─────────────── app（Android）───────────────┐
        │  UI(Compose) → state(ViewModel) → location   │
        │                      ↓                       │

                               │ 单向依赖
```

`core` 里没有任何 `android.*` import。好处：

以后抽成 KMP 模块或搬到后端也不用改。

### 1.2 状态层的数据流

`NavViewModel` 把「自动定位」与「手动修正」分成两组独立的状态流，最后合流：

```
GPS ──► BuildingLocator ──► autoBuilding ─┐
                                          ├─ combine ─► resolve() ─► NavUiState
气压 ──► FloorEstimator ──► autoFloor ────┤                 │
                          autoFloorState ─┤                 ├─ positionText
                          autoSource ─────┤                 ├─ route  (纯函数派生)
DataStore ──► manual ─────────────────────┤                 └─ needsManualFloor
用户搜索 ──► target ──────────────────────┤
定位中标志 ──► isLocating ────────────────┘
```

**关键点：导航结果不是「算一次存起来」，而是 `(position, target)` 的派生值。**

因此「用户改完位置后，导航立即重算」不需要任何显式刷新调用 ——
`manual` 一变，`combine` 重新执行，`route` 自然重算。这是把验收标准变成结构保证，
而不是靠记得在某处调用 `recalculate()`。

`resolve()` 里的优先级规则：

1. **手动修正优先**：`manual.buildingId` 能解析出楼栋就用它；
2. **楼层只在「没有手动指定楼栋」时才用自动结果** ——
   否则会出现「手动选了 B 栋、楼层却还是 A 栋 3 楼」这种自相矛盾的状态；
3. 只有当 `manual` 携带 elementId 时才用手动元素，否则重新取「离用户最近的元素」。

`relocate()` 是**唯一**会清空手动修正、楼栋锁定、气压基准并重新采用自动结果的动作。
它不重新订阅定位流 —— 流的订阅一直在跑，重复订阅会导致多次回调。

## 二、算法细节

### 2.1 楼栋定位（射线法）

`Geo.containsPoint(polygon, point)`：

- 从待测点向正东引射线，统计与多边形边的交点个数，奇数则在内部；
- 顶点正好被射线穿过的情况用半开区间 `(yi > y) != (yj > y)` 处理，避免重复计数；
- **落在边上视为「在楼内」** —— 室内 GPS 误差下贴边更可能是真的在楼里；
- 支持凹多边形（`GeoTest` 里用 U 形多边形验证了凹陷处判为外部）。

`BuildingLocator` 负责「不频繁跳楼栋」：

| 情况 | 行为 |
| --- | --- |
| 点在楼栋多边形内 | 锁定该栋 |
| 已锁定，位移 < 12 米 | 保持原楼栋，来源标为 `LastLocked` |
| 已锁定，位移 ≥ 12 米且落在楼外 | 只有当另一栋楼更近时才换 |
| 未锁定，点在楼外 | 60 米内就近吸附，避免「第一次定位差一点就没结果」 |
| 未锁定，点在 60 米外 | 返回 null，UI 提示手动选择 |

### 2.2 楼层判断（气压 → 相对高度 → 楼层）

```
                   ┌─ 滑动平均(窗口8) ─┐
P(t) ──► window ──►│  P̄              │──► h = h_ref + 44330·(1-(P̄/P_ref)^(1/5.255))
                   └──────────────────┘                    │
                                                           ▼
                            argmin |floor.relative_height_m − h|
                                                           │
                                  ┌────────────────────────┴──────────────┐
                                  ▼                                       ▼
                        离最近楼层 ≤ 6m                      离所有楼层 > 6m
                                  │                                       │
                     改善 ≥ 1.5m 才允许切换                    返回 null（不猜）
```

- **基准 `P_ref` / `h_ref` 的来源**：用户手动选定楼层时（`recalibrate`），或首次进入某栋楼时
  以当时气压为地面层基准（`anchor`）。换楼栋会重新校准。
- 为什么这样校准：气压绝对值随天气变化，硬编码 `P0` 必然漂移；
  用「用户给出真值那一刻的气压」当基准，只依赖气压计的**相对**分辨率（一层约 0.48 hPa）。
- `FloorMatcher.estimatedHeightM` 暴露推算高度，便于 logcat 排查「为什么判成这一层」。

`FloorMatcherConfig` 默认值（**需要真机调参**）：

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `windowSize` | 8 | 滑动平均窗口，抑制噪声 |
| `minSamples` | 5 | 少于此样本数不下结论 |
| `maxMatchDeltaM` | 6.0 | 离最近楼层超过此值认为气压不可信 |
| `switchThresholdM` | 1.5 | 切换楼层需要比当前楼层近多少米（滞后） |

### 2.3 走廊排序（PCA + 主方向吸附）

```
元素质心 ──► 局部米坐标(x=东,y=北) ──► 2×2 协方差主特征向量
                                              │
                                              ▼
                                    吸附到 ±(1,0)/±(0,1)
                                              │
                                              ▼
                        按「投影坐标 → 北侧优先 → 自西向东 → id」排序
```

- 局部坐标用 `Geo.toLocalMeters`：`x = Δlng · 111320·cos(lat)`，`y = Δlat · 110574`。
- 主特征向量解析求解（`trace`/`det` 公式），不引线性代数库。
- 符号统一为「东分量非负」，保证排序方向确定可测。
- **吸附**与**次级键**都是实测必需的，原因见第五节。

`CorridorOrder` 同时给出：
- `elements`：排好序的元素；
- `direction`：走廊主轴方位（八方位，如「向东」），决定文案里的「沿走廊向东走」；
- `leftVector`：沿主轴前进时的左手边法线，用于左右判定。

### 2.4 左右方位判定

```
lateral(p) = (p − origin) · leftVector          // p 在走廊主轴上的横向偏移

sideOf(reference, other):
    refSide   = sign(lateral(reference))
    otherSide = sign(lateral(other))
    if refSide == otherSide and otherSide != Center:  return otherSide
    return otherSide                                   // 两侧不同时同样取目标侧
```

实质就是：**目标在走廊的哪一侧，就是哪一侧**。
和「目标相对当前位置偏东还是偏西」无关 —— 同一间教室，从东边走还是从西边走，
它都在走道的同一侧，这与直觉一致，也不会给出自相矛盾的指引。

容差 `SIDE_TOLERANCE_M = 1.0`：横向偏移小于 1 米视为「走廊正中」（如入口、正对走廊的位置）。

### 2.5 三种导航路线

`NavigationEngine.route(current, target)` 按楼栋 / 楼层是否相同分派：

| 情况 | 组装方式 | 文案形态 |
| --- | --- | --- |
| 同楼同层 | `RouteText.sameFloor` | `从当前位置出发，沿走廊向东走，经过计算机房，目标数学教研室在左手边。` |
| 同楼跨层 | `verticalTransition` + `sameFloor` | `先沿走廊向东走，经过计算机房，到东楼梯口，上到 2 楼。` + `出楼梯后，沿走廊向东走，经过…，目标物理实验室在左手边。` |
| 跨楼 | `crossBuilding` + `sameFloor` | `先出A栋，B栋就在旁边，进楼后上到 2 楼。` + `出楼梯后，…` |

细节取舍：

- **跨层换乘点**：`findStair` 优先选**离当前位置最近**的楼梯口（没有楼梯时退回电梯口）。
- **人已经在楼梯口时**省略「先走到」：`你在东楼梯口，直接上到 2 楼。`
- **跨楼不编造出门点**：数据里没有「哪个门通向哪栋楼」的信息，
  所以跨楼文案只给楼栋级指引（`先出 A 栋，前往 B 栋`），不写「出南门右转」这种无依据的话。
  相邻 120 米内的楼栋说「B栋就在旁边」，更远则说「前往 B栋」。
- **中间元素过多**：超过 4 个时概括为 `经过计算机房等 7 个位置`，
  避免一次念十几间教室。

### 2.6 文案硬约束与对应断言

| 约束 | 实现 | 断言 |
| --- | --- | --- |
| 不出现米数 | 文案模板里没有任何距离字段 | `所有导航文案都不出现米数`（含 `\d+\s*(m\|M\|米)` 正则反向断言） |
| 不出现教室编号 | 模板只用 `element.name` | `所有导航文案都不出现元素 id` |
| 只列中间经过元素的中文名 | `between` 区间 + `joinToString("、")` | `同层导航列出中间经过的中文名` |
| 用「左手边/右手边/正前方/隔壁」 | `RouteText.sideText` + 两侧判定 | `目标与当前位置同在走廊同一侧时按目标所在侧给方位` 等 |
| 楼梯口/电梯口作为关键转向点 | `verticalTransition` 始终点名楼梯口 | `跨层导航提示先上到几楼并说明出楼梯后怎么走` |

`RouteStep.highlight` 携带需要在 UI 高亮的中文名，由 `HomeScreen` 用
`buildAnnotatedString` 加粗染色 —— 文案与样式分离，算法不碰 UI 概念。

## 三、Android 层实现要点

### 3.1 定位通道抽象

```kotlin
interface LocationSource {
    fun isAvailable(): Boolean
    fun locationUpdates(): Flow<RawLocationFix>
    val channelName: String
}
```

- `SystemLocationSource`：`LocationManager`，同时注册 GPS 与 Network provider，
  谁先给出可信点用谁。不依赖 Google GMS，国内 ROM 可用。
- `AmapLocationSource`：**反射接入**。检测不到 SDK 就 `isAvailable() == false`，
  `AppContainer` 自动落回系统定位。

**为什么反射**：高德 aar 只在自己的 Maven 仓库分发，网络受限环境拉不下来会把整个工程卡死。
反射让「有没有 SDK」变成运行时的可选性，而不是编译期的硬依赖。
代价是初始化时有一次类/方法查找（只做一次，逐点回调直接用查好的 `Method` 句柄）。

反射里已经处理高德 SDK 的隐私合规前置要求：

```kotlin
AMapLocationClient.updatePrivacyShow(context, true, true)
AMapLocationClient.updatePrivacyAgree(context, true)
```

—— 这两个必须在任何定位调用之前执行，否则高德 SDK 不返回结果。

### 3.2 传感器与协程生命周期

- 传感器用 `callbackFlow` 包装，`awaitClose` 里注销监听；
  `launchIn(viewModelScope)` 在 ViewModel 清理时自动取消 → 不会泄漏 `SensorEventListener`。
- 气压与定位都是**持续**订阅。气压样本大约每秒来几个，
  `combine` 会让 `NavUiState` 频繁重算；因为重算是纯函数且很轻（几十个元素的排序），
  实测没有性能压力。数据量上千后可以加 `distinctUntilChanged` 或抽到后台线程。

### 3.3 依赖注入

`AppContainer` 手写容器（5 个字段），比引 Hilt 更轻，依赖关系一眼能看全。
`NavViewModel.factory(container)` 是手写工厂。ViewModel 数量变多后再考虑 DI 框架。

## 四、数据生成

`tools/gen-buildings-json.mjs`：用「局部米坐标 + 矩形」描述每层布局，一次性换算成经纬度。

```
每层标准布局（局部米，原点在楼栋中心）:

      北侧一排教室 (y: 1 ~ 9)
  ┌──┬──┬──┬──┬──┐
  │  │  │  │  │  │
  ╞══╧══╧══╧══╧══╡  ← 走廊 (y: -1 ~ 1)
  │南门│楼梯│教室│教室│教室│电梯│   (y: -9 ~ -1，入口延伸到 y=1)
  └───┴───┴───┴───┴───┴───┘
```

- 换算常量与 `Geo` 保持一致：`110574 m/°lat`、`111320·cos(lat) m/°lng`。
- 产物是**静态 JSON**，App 运行时只读不生成 —— 符合产品文档「不做自动生成数据文件」的非目标。
- 生成后有自检兜底：`CampusRepository.validate()` 检查楼层高度递增、首层为 0、id 唯一等，
  `BuildingsDataTest` 针对真实文件跑这些断言。

**坐标系统一为 GCJ-02**：数据生成、App 内计算、高德 SDK 输出全部是 GCJ-02，
运行时**不做任何坐标系转换**。如果以后接入 WGS84 数据源，必须在入库前转好。

## 五、排查记录（踩过的坑）

留在这里是因为这几个坑都很容易再犯，而且**只有断言能挡住它们**。

### 5.1 `atan2` 参数顺序写反，方位整整差 90°

`bearingOf` 最初写成 `atan2(ux, uy)`（东, 北）。Kotlin 的 `atan2(y, x)` 是数学惯例的
`y` 在前，于是「向东」被算成 0° → 判为**向北**。

**症状**：文案出现「沿走廊向北走」，而走廊明明是东西向。
**修复**：`atan2(uy, ux)`，并在函数注释里写清「参数是 (北分量, 东分量)」。
**被谁挡住**：`走廊主轴方向判为向东`、`同层导航列出中间经过的中文名`。

### 5.2 PCA 主轴被数据小错位带偏 6°，左右判定翻转

这是最隐蔽的一个，靠读代码看不出来。

真实布局里「东楼梯口」在 x = −22，而北侧教室从 x = −20 开始，两者错开约 4 米（楼梯口宽 4 米、
教室宽 8 米，中心不对齐）。PCA 求出的主轴因此偏了约 **6°**，`leftVector = (−0.105, 0.994)`。

后果：**同一侧**的两间相邻北侧教室（`语文教研室` x=−11.09 与 `数学教研室` x=−3.09，
都在 y=+5），横向差 = `8 × (−0.105) = −0.84 米` —— 小于 1 米的「走廊正中」容差，
于是「目标在左手边」被误判成「**就在正前方**」。

排查方式：写了一个临时 `DebugOrderTest`，把排序结果、`leftVector`、每个元素的局部坐标与
`lateral` 值 dump 到文件里，一眼看到 `leftVector` 不是纯 `(0,1)`。

**修复（两步）**：

1. `snapToDominantAxis` 把主轴吸附到正东西/正南北，`leftVector` 变成纯净的 `±(0,1)`；
2. 左右判定改为「看目标在走廊哪一侧」，不再用相对当前位置的横向分量。

**被谁挡住**：`沿走廊前进时北侧元素在左手边`、`目标与当前位置同在走廊同一侧时按目标所在侧给方位`。

### 5.3 滑动窗口的瞬态让测试算出错误结论

`FloorMatcherTest` 里断言「气压降 0.73 hPa 应判为 3 楼」失败，实现给出的是 2 楼。

原因**不在实现，在测试算子**：滑窗长度 8，喂 1 个新样本时均值只移动 `1/9`，
实际生效的气压差只有 `0.73 × 8/9 ≈ 0.649 hPa`，对应高度 4.6 米 —— 更接近 2 楼。

**修复**：测试里加 `settle(pressure)` 辅助函数，喂满窗口让均值真正到位后再断言；
「需要多少气压差才能到某高度」改成用二分反算（`pressureDropFor`），不再手算。

**教训**：带状态滤波器的测试必须区分「瞬态」与「稳态」，否则测的是滤波器动态而非算法。
这条已经写进 `FloorMatcherTest` 的类注释。

### 5.4 相等排序键导致走廊顺序不可复现

走廊同一经度上可能同时有两个元素（fixtures 里用「卫生间」与南侧教室同经度来覆盖这种情况）。
只用投影坐标作键时，相等键的相对顺序不保证稳定，同一份数据可能排出两种走廊顺序，
导航文案随之不稳定。

**修复**：排序键补成「投影坐标 → 北侧优先（`−lat`）→ 自西向东（`lng`）→ `id`」，
最后用 `id` 做终极兜底，保证全序。投影坐标本身还要先量化到 1e-6 米，
否则 1.45e-9 米的浮点噪声会把次级键直接盖掉。

### 5.5 构建环境的两个坑（与本机沙箱有关）

1. **`app/build.gradle.kts` 里 `java` 被解析成 Java 插件扩展**：
   在 `run { ... }` 里写 `java.util.Properties()` 会报 `Unresolved reference: util`，
   因为 `java` 优先解析为 `JavaPluginExtension`。
   **修复**：文件顶部 `import java.util.Properties`，正文用 `Properties()`。
2. **Gradle 默认 512m 堆编译 Compose 会 GC 抖动甚至直接失败**：
   必须在 `gradle.properties` 里显式放大：
   ```properties
   org.gradle.jvmargs=-Xmx2048m -XX:MaxMetaspaceSize=768m -XX:+UseParallelGC -Dfile.encoding=UTF-8
   kotlin.daemon.jvmargs=-Xmx1536m -XX:MaxMetaspaceSize=512m
   ```

另外，本机 `.ps1` 脚本里的中文注释会被 Windows PowerShell 5.1 按 ANSI 解析导致语法错误，
所以 `tools/*.ps1` 刻意全部使用 **ASCII** 注释与输出。

### 5.6 多配置存储的两个自查出来的 bug

这两个都是写完多配置功能之后、被新补的用例当场抓出来的，属于「不加测试就一定会线上崩」：

**（一）`list()` 与 `activeFileName()` 互相调用 → `StackOverflowError`**

```
list()            -> activeFileName()      // 想标出「哪一份在用」
activeFileName()  -> list().firstOrNull()  // 想在指定的那份失效时回退到最新
```

结果是设置页一打开就崩，而且崩在 UI 线程上，表现为「点我的 → 设置，App 直接退出」。

**修复**：`list()` 只读 SharedPreferences 里记着的**原始名字**（`ActiveConfigStore.activeFileName()`），
不回退；回退逻辑只留在 `activeFileName()` 里。职责分开，环就断了。

**被谁挡住**：`ConfigStoreTest` 的「列表会标出当前生效的那一份和损坏的文件」「保存会同时写入内部与外部两份」等。

**（二）把配置改名成同一个名字，多出一份 `xxx-2.json`**

`rename` 的顺序是「先 `uniqueFileName` 查重，再和原文件名比」，于是填了同样的名字时
查重先看到一个同名文件，把它当成「撞名」，于是生成 `editor_buildings-2.json` 并改名过去。
症状是用户点「改名 → 直接确定」，配置莫名其妙多了一份。

**修复**：`rename` **先比显示名**，相同就直接返回原文件名；`sanitize` 顺手吃掉用户可能
带上的 `.json` 后缀，避免出现 `实验中学.json.json`。

**被谁挡住**：`改名到同一个名字是空操作`、`新建时带上 json 后缀不会变成双后缀`。

### 5.7 撤销为什么必须存「整份数据快照」

第一版撤销存的是「本次新画的点」，所以用户抱怨「已经写进配置的楼栋撤不回来」——
它不是 bug 修不修的问题，而是**模型选错了**：配置里读进来的楼栋和刚画出来的楼栋
在数据结构上完全一样，历史里却只记后者。

**修复**：`history: ArrayDeque<List<EditorBuilding>>`，每次改动前压入当前 `buildings`。
不区分来源，所以「删掉配置里的楼栋再撤销」也能回来。
配套两个细节：

- `MAX_HISTORY = 50`，避免长时间编辑把内存撑爆；
- `ShapeDrag` 把**一次拖拽（按下 → 若干次移动 → 抬起）合并成一步**，
  否则撤销一下只退回一个像素。

**被谁挡住**：`撤销能把配置里读进来的楼栋也撤回来`、`一次拖拽编辑只记一步历史`。
