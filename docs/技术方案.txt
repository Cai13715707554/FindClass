校园教学楼导航 Android MVP 技术方案

版本：1.0
日期：2026-09-25
适用平台：Android 独立 App
技术路线：Kotlin + Jetpack Compose + 原生传感器 + 高德定位 + 本地静态数据
后端策略：MVP 零后端

一、项目定位

面向学生、新生、访客的教学楼室内导航工具。
核心能力：

用 GPS 判断用户在哪个楼栋。

用气压计判断用户大概在几楼。

默认选择当前楼层最近元素作为当前位置。

用户可手动修改楼栋、楼层、当前位置。

搜索目标教室、办公室、实验室、楼梯口等。

生成中文文字导航，不用米数，不用教室编号。

MVP 不做地图绘制、不做平面图、不做 AR、不做 3D、不做室内连续定位、不做后台管理系统。

六、定位与楼层判断

楼栋定位
使用高德定位 SDK 获取经纬度。
用射线法判断点是否在楼栋 polygon 内。
在哪个楼栋内，就锁定哪栋楼。
室内 GPS 漂移时，保持最后锁定的楼栋。
不要频繁跳楼栋。

楼层判断
读取气压计 Sensor.TYPE_PRESSURE。
对气压值做滑动平均，降低噪声。
计算相对高度：
h = 44330 * (1 - (P / P0) ^ (1 / 5.255))
P0 为基准气压，可由用户校准。
将当前高度匹配到最接近的楼层 relative_height_m。
加阈值和滞后，避免楼层频繁跳动。
没有气压计或数据不可信时，允许用户手动选择楼层。

默认当前位置
在当前楼层所有元素中，找离用户最近的元素。
直接作为默认当前位置，不弹窗、不打断。
例如：A栋 · 3楼 · 语文教研室。

用户修正
顶部位置卡片提供“修改”。
可修改三级：楼栋、楼层、当前元素。
手动修改优先。
手动修改后，短时间内不被自动定位覆盖。
用户点“重新定位”后，才重新采用 GPS 和气压计结果。

七、导航算法

同层排序
计算同层元素质心。
沿走廊主轴方向投影排序。
得到顺序，例如：
入口 -> 语文教研室 -> 数学教研室 -> 东楼梯口 -> 化学实验室 -> 物理实验室 -> 电梯口。

同层导航
从当前位置到目标，取中间元素。
生成文案，例如：
从当前位置出发，沿走廊向东走，经过语文教研室、数学教研室，目标物理实验室在左手边。

跨层导航
先找到当前楼层楼梯口。
提示上/下到目标楼层。
出楼梯后，再按同层导航生成文案。
例如：
先走到东楼梯口，上到 3 楼。出楼梯后，沿走廊向东走，经过语文教研室、数学教研室，目标物理实验室在左手边。

跨楼导航
先出当前楼栋。
前往目标楼栋。
进楼后上/下到目标楼层。
出楼梯后，再按同层导航生成文案。
例如：
先出 A 栋，前往 B 栋，进楼后上到 2 楼。出楼梯后，沿走廊向西走，经过自习室、研讨室，目标图书馆在右手边。

文案原则
不用米数。
不用教室编号。
只用中文名。
用“沿走廊向东/西走、左手边、右手边、前方、隔壁”等描述。
楼梯口、电梯口作为关键转向点。
中间元素太多时，用“经过语文教研室等 6 个位置”概括。

十二、风险与对策

气压计缺失或噪声大
对策：手动修正兜底；滑动平均；基准校准；楼层滞后。

室内 GPS 漂移
对策：保持最后锁定楼栋；不频繁跳楼栋；允许手动改。

厂商权限和后台限制
对策：只申请必要权限；定位仅前台使用；适配国内主流厂商。

坐标系不一致
对策：统一 GCJ-02；数据录入时校验。

数据维护成本
对策：MVP 用静态 JSON；后续做可视化编辑器和管理后台。

导航文案不自然
对策：算法与文案分离；建立测试用例；后续众包纠错。

十六、总结

本方案采用原生 Android 路线：
Kotlin + Jetpack Compose + 高德定位 + 气压计 + 本地静态 JSON + 纯 Kotlin 导航算法。
MVP 零后端，先把“能找到教室”这件事跑通。
导航只列中文名，不说米数，不用教室编号。
后续再扩展可视化编辑器、后端数据管理和课表一键导航。
