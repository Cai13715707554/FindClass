## 三、数据模型

### 3.1 导航数据（`core.model`）

```jsonc
{
  "buildings": [{
    "id": "...", "name": "A栋",
    "polygon": [ { "lng": ..., "lat": ... }, ... ],   // 外轮廓，GCJ-02
    "floors": [{
      "level": 3,
      "display_name": "3楼",
      "relative_height_m": 8.0,                       // 相对地面层高度，首层必须为 0
      "elements": [{
        "id": "...", "type": "room", "name": "物理实验室",
        "points": [ { "lng": ..., "lat": ... }, ... ]  // 点串：面 / 圆（32 边）/ 单点
      }]
    }]
  }]
}
```

**`ElementType` 只有四种**：`room` 教室 / `office` 办公室 / `stair` 楼梯口 / `toilet` 卫生间。
旧数据里若残留 `elevator` / `entrance`，`ElementType.fromRaw` **降级成教室**而不是崩溃。

**所有图形统一用点串表示**（面、圆、点都是点串）。这是整套设计的地基：
导航算法（质心、走廊排序、左右判定）因此完全不需要为形状分叉。

### 3.2 编辑器数据（`core.data.EditorConfig`）

| 类型 | 说明 |
| --- | --- |
| `ElementShape` | `Rectangle` / `Circle` / `Point` / `Polygon` —— 只是**画法**，不是新数据类型 |
| `EditorMode` | 8 个模式：教学楼 / 自由轮廓 / 教室 / 办公室 / 圆形区域 / 自由多边形 / 楼梯口 / 卫生间。带 `label`、`elementType`、`needsBuilding`、`shape`，以及派生的 `isPoint` / `isPen` / `isOutline` |
| `EditorElement` | `id` / `type` / `name` / `points` / `toLevel`；`isPoint` 看点数，`isValid` 按形状判 |
| `EditorBuilding` | `id` / `name` / `polygon` / `floorCount` / `floors`；`toBuilding()` 展开成导航数据（跨层楼梯在每一层各生成一份） |
| `EditorConfig` | `schemaVersion` / `exportedAtMillis` / `buildings` |

`EditorBuilding` 的 companion 里是一批**纯函数几何工具**（都能单独单测）：

| 函数 | 用途 |
| --- | --- |
| `rectangleFromCorners(a, b)` | 拖拽画矩形 |
| `circleFromCenter(center, edge, segments = 32)` | 拖拽画圆（在**局部米坐标**里算半径，否则会变椭圆） |
| `rotate(points, degrees)` | 绕质心旋转（同样在米坐标里算） |
| `translate(points, dEast, dNorth)` | 整体平移 |
| `insertVertex(points, edgeStart, at)` | 边上插点 |
| `nearestVertexIndex` / `nearestEdgeStartIndex` | 命中判定（带米制容差） |
| `isValidPolygon(points)` | 至少有 3 个不重合的点 |

### 3.3 坐标系

**全链路统一 GCJ-02**，运行时**零坐标转换**。数据生成脚本在入库前就换算好；
高德 SDK 输出的也是 GCJ-02。以后若接入 WGS84 数据源，必须在入库前转好。

## 四、核心算法

### 4.1 楼栋定位：射线法

点在多边形内用标准 ray casting（`Geo.containsPoint`）。室内漂移导致的「出界」由
`BuildingLocator` 的**保持最后锁定**策略吸收。

### 4.2 楼层判断：气压 → 相对高度 → 最近楼层

```
P(平滑后) ──► h = 44330 · (1 − (P/P0)^(1/5.255)) ──► 与各层 relative_height_m 比最近
```

- `P0` **不硬编码**：用户在「修改位置」选楼层时，把当时气压记为该层基准。这样气压计的
  绝对偏差被消掉，只依赖它的相对分辨率（一层约 0.48 hPa）。
- 滑动平均窗口 8。
- 切换滞后 1.5 m；离所有层都超过 6 m → 返回 null。

| 参数 | 现值 | 状态 |
| --- | --- | --- |
| 滑动窗口 | 8 | 估值，待真机调 |
| 切换阈值 | 1.5 m | 估值，待真机调 |
| 最大匹配偏差 | 6.0 m | 估值，待真机调 |
| 假设层高 | 4.0 m | 估值，待真机调 |

### 4.3 走廊排序：PCA 求主轴 + **吸附到主方向**

1. 对该层元素的质心做 2×2 协方差矩阵 PCA，取主特征向量当走廊轴；
2. **把轴吸附到正东西或正南北**（`snapToDominantAxis`）；
3. 把每个质心投影到轴上，**量化到 1e-6 米**；
4. 用显式 `Comparator` 全序排序：投影 → 北侧优先（lat 降序）→ 自西向东（lng 升序）→ id。

**为什么必须吸附 + 量化**：

- 真实布局里「东楼梯口」与北侧教室列在 x 上错开约 4 米，PCA 主轴被带偏约 **6°**，
  导致同侧相邻教室产生约 1 米的假横向差，「左手边」被误判成「正前方」；
- 浮点噪声在 1.45e-9 米量级，不量化就会一直把次级排序键盖掉，
  同一份数据排出两种走廊顺序，导航文案随之不稳定。

### 4.4 左右方位：看「目标在走廊哪一侧」

不用「目标相对当前位置的横向分量」，而是看**目标自身落在走廊的哪一侧**。

理由：同一间教室，从东边走过去还是从西边走过去，它都在走道的同一侧。
沿走廊前进时北侧始终是左手边、南侧始终是右手边 —— 符合直觉，也不会因为
当前位置选在哪而给出互相矛盾的指引。

### 4.5 导航方向：用走廊主轴，不用两点连线

同层文案里的「向东走 / 向西走」取**走廊主轴方向**（排序正序为 `direction`，倒序取反向）。
两间教室一南一北错开几米时，两点连线的方位角会算出「向东北走」这种不自然的说法；
走廊是一条线，用户沿它走，「向东」永远是向东。

### 4.6 三种路线

| 情况 | 生成方式 |
| --- | --- |
| 同层 | 排序后取当前位置与目标之间的中间元素，串成「沿走廊向东走，经过 A、B，目标在左手边」 |
| 跨层 | 同层走到楼梯口 → 「上/下到 N 楼」→ 出楼梯后继续同层指引。**楼梯是唯一的跨层换乘点** |
| 跨楼 | 楼栋级指引：「先出 A 栋，前往 B 栋」。不做室外路径 |
| 已到达 | 「你已经在 X 了。」 |

### 4.7 文案约束

| 约束 | 保障方式 |
| --- | --- |
| 不出现米数 | `NavigationEngineTest` 正则反向断言 `\d+\s*(m\|M\|米)` |
| 不出现教室编号 / id | 文案模板只接受 `name`；`id` 从不出现在文案里 |
| 只用相对方位词 | 模板固定为 左手边 / 右手边 / 正前方 / 隔壁 |
| 全中文 | 所有文案常量都是中文字符串 |

## 五、状态层

### 5.1 `NavViewModel`

把「自动定位」与「手动修正」分成两组独立状态流，最后合流。**手动优先**。

```
GPS ──► BuildingLocator ──► autoBuilding ─┐
                                          ├─ combine ─► resolve() ─► NavUiState
气压 ─► FloorEstimator ──► autoFloor ─────┤                 │
                        autoFloorState ───┤                 ├─ positionText
                        autoSource ───────┤                 ├─ route（纯函数派生）
DataStore ──► manual ─────────────────────┤                 └─ needsManualFloor
                                          │
配置切换 ──► repositoryFlow ──────────────┘
```

**实现要点**：

- 派生状态需要 **8 个输入**，而 `combine` 最多 5 路，6 路以上只剩「接收 `Array<Any?>`」
  的重载，实测会让类型推断失败。所以改成**手动把多个 StateFlow 收进一个
  `MutableStateFlow`**（`autoLocate`、`sensorReadings`）。
- 最终 `uiState` 的 `combine` 正好用满 5 路，第 5 路就是 `repositoryFlow` ——
  **用户切换学校配置后首页要跟着换数据**。
- 导航结果是 `(位置, 目标)` 的纯函数派生值，所以任何一方变化都自动重算。

### 5.2 `MapEditorViewModel`

| 状态 | 说明 |
| --- | --- |
| `mode` / `targetBuildingId` / `floorLevel` / `endFloorLevel` | 当前工具与落点上下文 |
| `draftPoints` / `dragStart` / `draftName` / `draftFloorCount` | 绘制中的预览 |
| `buildings` / `lastSave` | 成果 |
| `editMode` / `selection` / `editAnchor` | 编辑形状：选中谁、最近点了哪 |
| `canUndo` / `canRedo` | 按钮可用性（含「有钢笔草稿」） |
| `configs` / `activeConfigName` | 多配置 |
| `myLocation` / `locationUnavailable` / `centerRequest` | 定位与「把地图移过去」的请求 |

**两条设计原则**：

1. **不依赖高德 SDK**：地图渲染在 `AmapEditorView`，通过回调把「用户点了哪 / 拖到哪」
   传进来。所以绘制与编辑逻辑能在纯 JVM 上单测。
2. **历史存整份快照**：`ArrayDeque<List<EditorBuilding>>`（上限 50）+ 重做栈，
   不区分「配置里读进来的」和「本次新画的」。

**撤销的两条特殊规则**：

- 一次拖拽用 `ShapeDrag`（记录手势起点的**原始点串**）合并成一步 ——
  既避免「撤销一下只退回一个像素」，也避免在上一帧结果上累加偏移导致图形慢慢飘走；
- 钢笔草稿优先退点：`canUndo` 把「有钢笔草稿」也算作可撤销。

## 六、Android 层

### 6.1 依赖容器

`AppContainer` 手写容器，比引 Hilt 更轻，依赖关系一眼看全。所有对象懒加载、进程内单例。

```kotlin
val configStore: ConfigStore          // 多配置（要先于 repository 建好）
val apiKeyStore: ApiKeyStore          // 两个高德 Key
fun loadRepository(): CampusRepository // 按当前生效配置装配
val repositoryFlow: StateFlow<CampusRepository>  // 切换配置 / 存盘后通知所有订阅者
val repository: CampusRepository
fun reloadRepository()
val locationSource: LocationSource    // 高德可用则高德，否则系统
val altimeter: BarometricAltimeter
val preferences: UserPreferences
```

**注意**：`locationSource` 是惰性的 —— 填完 Key 需要**重启 App** 才生效。

### 6.2 定位通道抽象

```kotlin
interface LocationSource {
    fun isAvailable(): Boolean
    fun locationUpdates(): Flow<LocationUpdate>   // Fix 或 Unavailable(reason)
}
```

- 返回类型从 `Flow<RawLocationFix>` 改成 `Flow<LocationUpdate>` 是关键：
  **空流无法表达「为什么取不到点」**，改之前表现为「中途关掉定位服务后永远转圈」。
- `LocationAvailability` 区分 `PermissionDenied` / `ServiceDisabled` / `NoProvider`。
- 两个实现：`SystemLocationSource`（默认）、`AmapLocationSource`（反射接入，可选）。

### 6.3 数据装配

`CampusAssets.loadRepository(context, configStore)`：

```
assets/buildings.json  ──┐
                          ├─► mergeOne：按楼栋名匹配，逐层合并（保留没被覆盖的层）
<config>/当前配置.json  ──┘
```

合并粒度是**逐层**而不是整栋替换 —— 否则编辑器只改了 3 楼，1、2 楼会被清掉。

`CampusRepository.validate()` + `mergeWarnings` 做数据自检：多边形点数、楼层高度递增、
首层为 0、id 唯一、元素有中文名与几何点。**自检结果只打日志，不崩溃** ——
「能用手动模式走通」比「启动即报错」更有用。

### 6.4 多配置存储

见 `01-功能清单.md` §4。技术上要注意两点：

- **`list()` 不能调用 `activeFileName()`**：后者在指定文件失效时会回退并调用 `list()`，
  两者互相调用会直接 `StackOverflowError`。`list()` 只读 SharedPreferences 里的**原始名字**。
- **写入是原子的**：先写 `.tmp` 再 `renameTo`，写到一半被中断也不会留下半截 JSON。
- 外部那份写失败只降级为 warning，内部那份才是权威（`SaveResult.warnings`）。

### 6.5 Key 存储

`ApiKeyStore`（`SharedPrefsApiKeyStore`，prefs 名 `amap_settings`）：

| Key | 用途 |
| --- | --- |
| `amapKey()` | Android 平台，地图渲染 + 定位 |
| `amapWebKey()` | Web服务，POI 文本搜索 |

**Key 不打进 APK**，由用户在设置页填。`local.properties` 里的 `amap.key` 只用于
debug 时预填输入框，不参与任何构建期常量注入。

### 6.6 搜索后端

`PoiSearcher` 是统一入口，`PoiResult` 归一化两边的差异：

```
有 Web服务 Key ──► AmapPoiSearcher：restapi.amap.com/v3/place/text（HttpURLConnection）
                        ↓ 失败
                    Android Geocoder（精确地址解析）
无 Web服务 Key ──► 直接走 Geocoder
```

匹配策略：完全相等 → 包含 → 前缀 → 后缀（后缀候选砍到 ≤3 字再比）。
地理编码的候选会做「去掉后缀词」的放宽尝试。

### 6.7 地图渲染层

`AmapEditorView` 的两条核心策略：

1. **关掉所有高德自带控件**（缩放按钮、指南针、比例尺、定位按钮），只保留法律要求的 Logo。
   高德的视觉语言和本应用（胶囊导航 + 白色圆角卡片 + 蓝绿强调色）摆在一起很割裂。
2. **每次状态变化就清空 overlay 后整体重画**。元素只有几十个，重画开销可忽略，
   换来的是不需要维护「哪个 overlay 对应哪个顶点」的增量状态 ——
   那种写法很容易留下幽灵多边形。**只清 overlay、不动相机**，
   用户拖地图时不会被拉回原位；需要移动相机时走 `centerRequest`（带 token，消费一次失效）。

**地图常驻组合树**（`AppShell`）：

```
Box
 ├── MapEditorScreen(active = onMapTab, modifier = Modifier.visible(onMapTab))  ← 永远在树里
 └── SaveableStateProvider(pageKey) { when { 设置 / 首页 / Map→Unit / 我的 } }
 └── BottomNavBar
```

`active=false` 时 `AmapEditorView` 自己把 `MapView` 设成 `INVISIBLE` 并解除点击监听。
**一旦离开组合树，`MapView` 对象就会被销毁重建，相机位置与 overlay 全丢** ——
表现就是「切回来地图刷新了」。早先试过把它提到 Activity 作用域（只解决状态重建）、
换成 `movableContentOf`（`AndroidView` 移动时 View 仍被重建），都不行。

## 七、构建与验证

```powershell
# 交付前全量
powershell -File tools/gradle.ps1 :core:test :app:testDebugUnitTest :app:assembleDebug

# 迭代时只跑相关子集
powershell -File tools/gradle.ps1 :app:testDebugUnitTest --tests "*MapEditorViewModelTest"
```

| 任务 | 结果 |
| --- | --- |
| `:core:test` | 7 个测试类 80 个用例，0 失败（1 skip 是平台相关的有序性检查） |
| `:app:testDebugUnitTest` | 4 个测试类 105 个用例，0 失败 |
| `:app:assembleDebug` | arm64-v8a 42.7 MB / armeabi-v7a 36.4 MB / universal 55.6 MB |

**本机的两个环境坑**（`tools/gradle.ps1` 就是为它们存在的）：

1. 沙箱不允许写 `%USERPROFILE%\.gradle`，所以 `GRADLE_USER_HOME` 指向仓库内 `.gradle-home/`；
2. 全局 `gradle.properties` 里配了不可达的 `localhost:7890` 代理，脚本用 `-D` 参数清掉。

脚本里的路径查找要**两层**：`<dist>/<hash>/gradle-8.13/bin/gradle.bat`。
只找一层会永远找不到缓存，于是又落回联网的 wrapper 而超时。

## 八、已知技术债与风险

| 项 | 影响 | 备注 |
| --- | --- | --- |
