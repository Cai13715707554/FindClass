# 工作梳理 · 索引

这套文档是给**现在这个项目的负责人自己看的**：把「已经做完了什么、怎么做的、长什么样、
点下去会发生什么」四件事各写一份，方便在改动之前先想清楚，而不是靠翻代码回忆。

和 `docs/` 下其它文件的分工：

| 文件 | 性质 | 什么时候看 |
| --- | --- | --- |
| `docs/产品设计文档.txt` | **原始需求**（用户视角、验收标准） | 想知道「当初要做什么」 |
| `docs/技术方案.txt` | **原始技术方案**（选型、算法草案） | 想知道「当初打算怎么做」 |
| `docs/Demo.html` | **原始交互 Demo** | 想知道「当初长什么样」 |
| `docs/技术方案落地说明.md` | **实现映射 + 踩坑记录** | 想知道「当时为什么这么改」 |
| `README.md`（仓库根） | 交付说明、构建命令、已知问题 | 想把 APK 跑起来 |
| **`docs/工作梳理/`（本目录）** | **现状快照**：功能 / 技术 / 视觉 / 交互 | 想理清「现在到底做到哪一步」 |

原始文档是**需求**，本目录是**现状**。两者冲突时以本目录 + 代码为准，
并且要把冲突记到 `01-功能清单.md` 的「有意偏离」一节里。

## 一、四份文档各管什么

| 文档 | 回答的问题 | 主要读者 |
| --- | --- | --- |
| [`01-功能清单.md`](01-功能清单.md) | **有什么功能？做到什么程度？** 已完成 / 未真机验证 / 明确不做，各一条 | 你（排优先级、跟人讲需求） |
| [`02-技术方案.md`](02-技术方案.md) | **怎么实现的？** 模块、数据、算法、状态流、存储、构建 | 你（改代码前）、以后接手的开发 |
| [`03-UI风格.md`](03-UI风格.md) | **长什么样？** 色板、字体、圆角、组件、地图配色、文案风格 | 你（加新界面时照着抄）、设计 |
| [`04-交互逻辑.md`](04-交互逻辑.md) | **点下去会发生什么？** 每个页面的手势、状态机、反馈文案、边界处理 | 你（加交互前先查有没有冲突） |

**建议阅读顺序**：先 `01` 明确范围 → 再 `04` 想清交互 → 再 `03` 定样式 → 最后 `02` 看怎么落地。

## 三、改动本目录的约定

- 这里写的是**现状**，不是计划。做了新功能要回来改，不要只加不删。
- 「未验证」项验证过了要挪到「已完成」，不要留着模棱两可。
- 任何一条**偏离原始文档**的决定，都要在 `01-功能清单.md` 里留一行，写清原因。
- 交互改动先改 `04-交互逻辑.md`，再改代码 —— 这份文档的作用就是让改动前先想清楚。

> 仓库根 `README.md` 面向「拿到 APK 的人」，本目录面向「维护这个项目的人」。
> 两边都要保持可读，但**不要互相复制大段内容**，重复的地方只留一句指路。
